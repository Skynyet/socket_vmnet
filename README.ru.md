# SkyNyet socket_vmnet: сеть с общей памятью для Lima VZ

[English version](README.md)

Это proof-of-concept (PoC): пара форков [socket_vmnet v1.2.2](https://github.com/lima-vm/socket_vmnet/blob/v1.2.2/README.md) и [Lima v2.2.0](https://github.com/lima-vm/lima/blob/v2.2.0/README.md). Они не являются официальными релизами.

## Зачем

Основная мотивация — ускорить shared-сеть ванильной пары. Ретрансляция каждого Ethernet-кадра через stream-сокет добавляет переключения между процессами, копирование и системные вызовы на пути трафика, которому вообще не нужен vmnet.

Начальная версия использовала отдельный координатор обмена через shared memory; в этом форке координатор встроен *непосредственно* в `socket_vmnet`. Hostagent каждой из двух (и более) Lima VM обменивается кадрами через общие кольцевые буферы в разделяемой памяти. Демон подключается к шине как выход в vmnet, так что гостевым VM по-прежнему доступны хост и внешняя сеть. Для обнаружения и подключения к шине служит **дополнительный Unix-сокет**: у сети Lima `shared` он называется `socket_vmnet_shm.shared` и находится рядом с исходным `socket_vmnet.shared`.

## Возможности и исправления

- **Шина с общей памятью включена по умолчанию; старый сервис сохранён.**
- **Рассылка между участниками шины не блокируется.** В upstream framed-ретранслятор может задержать всех клиентов, если одна VM перестала читать. Этот форк использует независимые курсоры кольцевых буферов в разделяемой памяти вместо блокирующей записи в сокет; занятый слот, удерживаемый получателем, приводит к потере кадра, а не к ожиданию остальных клиентов.
- **Безопасный жизненный цикл участников.** Протокол управления различает поколения подключений и сохраняет прежние отображения памяти, пока ими ещё могут пользоваться, в том числе при прерванном подключении VM или перезапуске координатора. Ванильная версия этого не поддерживает и требует перезапуска всех VM, использующих затронутую shared-сеть.
- **MTU vmnet и шины.** `--vmnet-mtu=BYTES` позволяет задавать MTU для shared- или host-режима vmnet; собственная шина демона наследует эффективное значение. Ограничения на несовпадение MTU отдельной VM и шины намеренно нет: это может быть полезно, например для тестирования PMTU discovery. Jumbo frames (например, MTU 9000) способны существенно повысить быстродействие сети.
- **Надёжный fallback.** Framed-reader собирает заголовок и тело кадра при коротких чтениях, повторяет прерванное чтение и отклоняет обрезанные или некорректные кадры. Это важно при отключённой шине и для клиентов, работающих только со старым протоколом.

## Быстродействие

- При MTU 1500 ванильная Lima с upstream `socket_vmnet` дала 2,38 Gbps между двумя VM; шина с общей памятью — 9,88 Gbps (23,4 Gbps при MTU 9000).
- С подключённым vmnet-uplink пара VM держала около 5,67 Gbps **в каждом направлении (bidir)** при MTU 1500 и четырёх TCP-потоках на направление.
- Остановка и повторное подключение третьей, простаивающей VM не прервали обмен host↔VM: 7,91, 7,84 и 7,72 Gbps. После отключения vmnet-uplink две VM продолжили обмен.
- Пакетная обработка на границе VZ в парном форке Lima снизила расход CPU hostagent на 30,2% в расчёте на GB.

QEMU и другие клиенты только с framed-протоколом не получают быстрый путь через общую память.
